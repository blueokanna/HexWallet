# 墨水屏与摄像头

## 面板配置

2.9 寸是尺寸，不是协议标识。板 7（`HEXWALLET_BOARD=7`）使用下列显式配置：

| `HEXWALLET_EPD_PROFILE` | 面板 | 刷新 |
| --- | --- | --- |
| 0，默认 | SSD1680 黑白 128×296；面板批次由板级负责 | 全刷；局刷走控制器 OTP 波形，需要 tuned 波形时板级自带 159 字节 `HEXWALLET_EPD_PARTIAL_LUT` |
| 1 | SSD1683 类四色 2.9 寸，128×296，黑/白/红/黄 | 2bpp 全刷，BUSY 低有效；不允许局刷 |
| 2 | SSD1680 黑白 128×296 V2 变体 | 局刷走 OTP 波形，BUSY 高有效 |

选配前核对完整模组型号。168×384 的 JD79667 四色屏、UC8151 黑白屏、SSD1680 四灰阶
都不能使用四色配置。未知屏幕不能按尺寸自动识别；默认配置也不是对当前实物的识别结论。

四色档位（`HEXWALLET_EPD_PROFILE=1`）还要求板级在自己的 pins 头文件里定义
`HEXWALLET_EPD_COLOR_INIT`——一个由 `EinkInitCommand{命令, 长度, 参数}` 组成的初始化表。
驱动不提供默认值：那些寄存器内容决定升压、上电时序和波形档位，写错比不显示更糟。没定义
表就选四色，`begin()` 直接失败，串口打 `ERR: e-paper panel did not initialise`，不会退化成
一块看起来能用的灰屏。

`EinkFrame` 负责 RGB565 到 1bpp/2bpp 转换；`EinkPanel` 负责控制器命令、窗口、BUSY 超时和
刷新计数；`WalletBoardPort` 只负责 SPI、引脚与 LVGL 接线。四色使用独立的初始化及
`0x10` RAM / `0x12` 刷新路径，不再复用 SSD1680 的 `0x24` / `0x22` / `0x20`。

局刷波形来自控制器自带的 OTP：驱动不再向 `0x32` 写入任何厂商波形表，仓库里也没有第三方
代码或数据文件。没定义表就直接用 OTP，`partial_supported()` 在黑白面板上恒为真；若某批
面板的 OTP 波形不合适，板级在自己的 pins 头文件里定义 159 字节 `HEXWALLET_EPD_PARTIAL_LUT`：
前 153 字节写 `0x32`，其后依次是 EOPT（`0x3f`）、VGH（`0x03`）、VSH1/VSH2/VSL（`0x04`）、
VCOM（`0x2c`）。只给波形不给电压的裸表会被 `begin()` 拒绝——那是刷新不干净和残影的常见成因。

黑白帧内 1 表示黑，发送时翻转为 SSD1680 的 0 表示黑。一次 RAM 上传只发一次 RAM 命令，
后续分块发送数据，避免每行重新发送命令造成寻址歧义。全刷建立旧/新 RAM 基线；局刷完成后
同步旧帧。首次更新或八次局刷预算耗尽时全刷，局刷窗口必须按字节对齐。切回全刷会重新初始化
完整刷新模式。四色始终全刷，不能因为画面只使用黑白就调用局刷。

显示端只在刷新成功后释放批准屏障；BUSY 超时或 SPI 失败不会把待显示交易当成已经显示。
刷新目前同步执行，等待上限为全刷 45 秒、局刷 4 秒。这是故障边界，不是实测刷新耗时；
尚未实现独立显示任务，长期 NFC/USB 并发延迟仍需优化与实机验收。

板级配置沿用仓库保存的 `c26102103` 网表；当前实物接线需要另行核对。面板和 PN7161 共用
SPI 总线、各用独立片选。初始化、局刷温度范围、全屏四色、残影、反复休眠、断电恢复和
异常 BUSY 都需要在目标板上测试，主机命令记录器不能替代这些检查。

初始化命令取自 SSD1680/SSD1683 数据手册公开的寄存器约定（命令字、参数位、时序），由本仓库
自行编写；没有引入厂商驱动源码，也没有第三方位图、波形或代码文件。

下文摄像头接线结论仅针对仓库保存的旧网表，不代表已检查当前实物。

## 摄像头 OV9281（SCCB 探测到位，CSI 流未实现）

OMNIVISION OV9281 是 **MIPI CSI-2** 器件（1280×800 全局快门，8/10-bit RAW），
寄存器走 **SCCB**（OmniVision 的 I2C 变体，写地址 0x60）。它能做的事分两层：

| 层 | 状态 |
| --- | --- |
| SCCB 读寄存器、读 chip ID（0x300A/0x300B → 0x9281） | **已实现**，`CameraPort.cpp`，主机自检覆盖 ACK/NAK/错型号/缺回调 |
| CSI-2 收流、ISP、解 QR | **未实现**。需要模组厂商的寄存器表 + `esp_cam_ctlr` CSI 配置 |

第二层没有写，是因为没有寄存器表就只能编一张，编出来的相机返回噪声；把噪声当“扫到的
地址”比明确说“没有相机”危险得多。`camera_probe()` 的返回值和 NFC/SE 一样是四分状态：
`NotConfigured` / `NoResponse` / `WrongSensor` / `PresentUnverified`，**没有**“已支持”这种
说法。

### 这块板子上的摄像头接了吗

没有。工程 `c26102103` 里可以逐条对上：

- ESP32-P4 的 CSI 焊盘 42–48 有网络，但都只接到串联电阻 R31–R37，电阻另一侧没有连接器；
- 板上的相机 FPC（26 pad，位号 `be25a532e5d3def2`）**所有焊盘都没有网络**；
- OV9281 只出现在丝印/文本层（`Designator: OV9281`），没有 SCCB、没有 MCLK、没有
  RST/PWDN 连到 P4。

所以 `HEXWALLET_CAMERA_*` 一个都没定义，`board_camera_probe()` 在这块板上返回
`NotConfigured`。等下一版把 SCCB 与 CSI 接出来以后，只需要在板级配置里补
`HEXWALLET_CAMERA_SCCB_SDA/SCL`，探测路径立刻可用；CSI 收流仍需要厂商寄存器表。

## QR 码

`QrCode.h/.cpp` 自带编码器与 1bpp 渲染器，不依赖第三方库：

| 项目 | 支持范围 |
| --- | --- |
| 版本 | 1–10（21×21 … 57×57） |
| 纠错 | **L、M、Q、H 全支持** |
| 模式 | byte（地址、xpub 指纹、配对码） |
| 容量 | v1-H 7 字节 … v10-L 271 字节；v10-Q 151、v10-H 119 |
| 策略 | 钱包默认 **H → Q → M 逐级降级，绝不低于 M** |
| 拒绝 | 空载荷、超出容量（绝不截断）、版本不在表内 |

**为什么默认从 H 开始。** 墨水屏对比度低、刷新后有残影，手机还常常是斜着扫的；同一段
地址用 H 编码只是让符号大一号，换来的是更强的纠错余量。只有载荷真的装不下时才退到 Q，
再退到 M（例如带 memo 的长 URI），**绝不会**悄悄降到 L——一个擦伤就扫不出来的码，不如
让用户手抄地址。

等级选择在 `qr_encode_best()` 里，调用方拿到 `chosen` 后会在屏上标出等级（H/Q/M），
用户与宿主都能看出这次用的是哪一档。

**为什么要做到 v10，而不是停在 v3。** v3-L 只有 53 字节，Kaspa 地址
（`kaspa:q…`，70+ 字符）、IOTA bech32、带 memo 的 URI 全部放不进去。真机地址里最长的一类
必须能编码，否则“支持 QR”只是对小字符串成立。v4 起有多 RS 块，v7 起要写版本信息块，
这两块都在这里实现了，没有跳过。

块结构与交织是最容易写错的地方，所以校验分两层：

1. **自检**（设备与主机都跑）：读回矩阵 → 重解两份格式信息 → 反掩码、反 zigzag →
   **反交织**成各块的数据+EC → 每块 RS 校验子必须为零 → 解析 byte 模式头并把载荷逐字节
   比对。v1–v10 × L/M 每个组合都用“刚好装满容量”的载荷跑一遍，还要证明多一个字节会被拒绝。
2. **交叉校验**（`tests/host/qr_cross_check.ps1`）：自检只能证明“编码器和自己的解码器
   一致”，而**格式信息两份写反**这种 bug 恰恰是自洽但扫不出来的。这个脚本把
   `QrCode.cpp` 与 nayuki/QR-Code-generator（固定 commit）编进同一个二进制，逐个模块
   比对 v1–v10 × L/M/Q/H × mask 0–7 共 **320** 个矩阵。当前结果：
   `cases=320 matrix_mismatches=0`。

这一步真的抓到过东西：此前 v1–v3 的实现把格式信息第一份的纵向/横向两半调换了，符号
“看起来像 QR 码”，实际扫不出来。修法是把 bit 0–5 放到 8 列（列 8 向下），bit 9–14 放到
第 8 行向左——参考实现就是这么摆的。

**仍然没有验证的事情**：真机扫描器。上线前必须用手机扫一张屏上的码——这一步只能你在
台面上做，我不会写成“已验证”。

### 屏上的 QR 是怎么画的

`nothing_qr()` 把矩阵写进 LVGL 的 **I1（1bpp）canvas**，调色板只有纸色和墨色两项，
再用**整数倍** `lv_image_set_scale` 放大：非整数缩放会让模块落在半像素上，在墨水屏上
就是一片灰糊，扫不出来。canvas 的 stride 用 `lv_draw_buf_width_to_stride()` 取，不自己
猜对齐规则。像素缓冲与 `QrCode`（3.3 KiB）都是静态的——一个屏幕只有一个码，不该为此
在栈上再开一份。

地址超长或编码失败时**不画半截图**，而是显示 `QR UNAVAILABLE - USE ADDRESS`：宁可让用户
手抄地址，也不能给出一个扫出来是别的内容的码。


## 伙伴：DeepSeek-chan（`Mascot`）

主屏使用用户参考图衍生的长发、女仆头饰、鲸尾角色，短名为 `DS-CHAN`。
原图、生成说明、可复现转换脚本与像素预览见 [素材说明](../assets/mascot/README.md)。
八张 64×64 单色位图共 4 KiB，通过独立的 `MaidSprite` 模块提供给 LVGL canvas。
128 像素宽的屏幕采用纵向排列，角色不受全局字号缩放影响，不会被裁成半张脸。

状态仍有 `Calm / Happy / Alert / Angry / Eating / Excited / Working / Sleep / Shy`。
现有位图叠加四帧代码效果，包括眨眼、星光、进食和休眠提示；部分状态仍共享角色原画。
工作状态优先，其次是进食、饥饿、休眠和互动反应。canvas 在主页生命周期内复用，
切页前撤销所有角色指针，LVGL 删除回调再清理一次，避免旧指针误改交易文字。
确认和拒绝交易均恢复中性表情，不加分、不扣分、不升级；亲密度仅来自主动互动。
宠物不会出现在交易审阅页。

I1 canvas 的头八字节是两项 ARGB8888 调色板，像素从第九字节开始，行跨度由
`lv_draw_buf_width_to_stride()` 决定。QR 和宠物均遵守此布局，避免调色板覆盖像素。
### 动起来的唯一前提是局刷

`wallet_ui_service()` 里只有当 `board_partial_refresh_supported()` 为真时才推进动画帧。
理由很直接：一帧全刷要 1–2 秒，为了眨个眼把整屏刷一遍，签名流程会被拖死。当前板子上
这个函数返回 **false**（缺面板批次波形 LUT），所以她停在第一帧；把 LUT 配进
`HEXWALLET_EPD_PARTIAL_LUT` 之后动画立刻生效，代码一行不用改。

### 三条刻意的限制

1. **不碰密钥、不读种子**，也永远不会改变签名结果——只对已经发生的事做反应。
2. **不自己排刷新**：帧请求由事件驱动并限流，动画每帧间隔 2.4 秒；没有已验证局刷能力时不推进画面。
3. **时间戳不落盘**：`millis()` 跨重启没有意义，饥饿从“刚喂过”重新开始，情绪永远是推导的。

### 能力与按键

| 能力 | 实现 |
| --- | --- |
| 按键互动 | FEED / PET / PLAY 三个按钮；无触屏板子走四键 keypad indev |
| 成长 | 25 点/级、最高 9 级；玩耍 +3、喂食 +2、抚摸 +1；批准和拒绝均为 0 |
| 亲密度条 | 8 段分段计量器，实心=已得、空心=未得 |
| 主动提醒 | 备份 > 低电量(<3.3 V) > 饿 > 未配对 |
| 统计 | 屏上 approved / rejected；完整计数在 `MascotStats` |
| 持久化 | 单键 NVS blob（`hexpet/state`，magic 校验），只存计数与亲密度 |

### 四键 keypad indev

P4 板只有 SW1–SW4、没有触屏，所以 `WalletBoardPort.cpp` 增加了键键盘输入设备：
SW1=上一个、SW2=下一个、SW3=确定、SW4=返回，25 ms 去抖。它同时解决了**审阅页按不到
APPROVE** 的问题——以前没有触屏就只能靠 CLI 批准。LVGL 默认 group 会自动收下按钮。

## 视觉语言（1bpp 下的 "Nothing" 风格）

墨水屏只有黑白，不能靠渐变或半透明表达层次。可用的手法只有三种，规则也就三条：

1. **纯黑 #000 / 纯白 #FFF**，没有第三种颜色。层次靠留白和线宽，不靠灰。
2. **点阵装饰**：标题下方用 1 像素点阵带（`• • • •`），与 Nothing 的点阵字形同构；
   点阵密度就是“层级”。
3. **分段计量条**：金额、进度用等宽分段（例如 12 段），段与段之间留 1 像素白缝。
   它在 1bpp 下没有抗锯齿问题，比实心条更清晰。

字体只用两档：地址/金额用等宽（逐字符核对），标签用无衬线大写 + 字距加宽。不要用
斜体，1bpp 斜体在 128 像素宽上会糊成一团。

### 代码里的三个原语

`WalletUi.cpp` 把这套语言收敛成三个函数，屏幕代码只组合它们，不各自发明样式：

| 原语 | 作用 |
| --- | --- |
| `nothing_dot_band(parent, n)` | 标题上方的点阵带，圆点直径与间距都走 `sc()` |
| `nothing_rule(parent)` | 1 px 分隔线，用来断开“标题 / 内容” |
| `nothing_micro_label(parent, text, accent)` | 大写小标签，字距 `sc(2)`，强调色只给必要的一处 |

地址还有两条硬规则：

- **每 4 个字符插一个空格**（`nothing_group_address()`）。地址本身不变，但人眼核对
  时分组比一整行 62 个字符快得多，也更容易发现抄错的位置。
- 地址块用 1 px 强调色边框单独框起来，禁止省略号与横向滚动——被截断的地址是资金事故。

审阅页同样是点阵带 + 强调色标题 + 1 px 分隔线的组合，金额和地址各自独占整行宽度，
不让长金额把目标地址挤掉。

## 币种图标（`CoinIcons`）

审阅页标题左侧的币种图徽是**真图标**，不是风格化代用品，但它在到达固件之前已经被压成
这块面板唯一能诚实显示的形式：1bpp 掩码。

- 源图来自 [cryptocurrency-icons](https://github.com/spothq/cryptocurrency-icons) 的
  `32/icon/<ticker>.png`（CC0 1.0，原始许可文本在 `assets/icons/LICENSE`）。下载后的 PNG
  原封不动放在 `assets/icons/32/`，没有本地重绘。
- `tools/pack_coin_icons.ps1` 把它们转成 32×32 的 I1 位图（每行 4 字节、MSB 在前、共 128
  字节），写入 `src/generated/CoinIcons.inc`。**固件里没有 PNG 解码器**，也没有文件系统：
  镜像里只有像素。
- 掩码的“墨”不是固定阈值，而是以该图标自身不透明像素的平均亮度为界：亮的字形在较暗的圆盘
  里会被挖空，1bpp 下仍然认得出；如果这条规则给出的是空图或几乎全实心（<10% 或 >90% 墨），
  打包器退回 alpha 剪影并打印提示。任何一个图标覆盖率低于 20% 都会让打包器直接报错。
- 表是 `{key, 位图, 字节数}`，key **大小写敏感且精确匹配**，键同时收录 ticker 与审阅页实际
  打印的全名（`ZEC`/`ZCASH`、`SOL`/`SOLANA`、`TRX`/`TRON`……）。查不到就**不画图标**——
  `NEAR`、`TON`、`CKB`、`KAS`、`SUI`、`HIVE`、`OSMO`、`TIA` 上游没有图，就保持没有。
  在“要不要把钱转出去”这一屏上，一个看起来像但其实是别的币的图徽，比空白危险得多。
- 绘制走 I1 canvas（与 QR 码同一套 `lv_draw_buf_init` + `lv_canvas_set_palette`），调色板
  取主题的纸色与墨色，所以深浅主题下都不用第二份数据，也不会被缩放插值糊掉。
- 图标由标题里那个**已被审阅封印覆盖**的网络字符串查表得到，因此没有任何新增的、未被封印的
  显示通道。`run_coin_icon_self_tests()` 会检查：键唯一、每个位图恰好 128 字节、墨量在
  10%–90% 之间、任两个不同图标的字节不相同（防止打包器把同一个文件映射到所有键）、
  未知键与错误大小写必须返回空。

## LVGL 许可

LVGL 从 v8 起就是 **MIT**：可以商用、可以闭源分发、个人开发者不需要购买任何授权。
`lvgl.io/open` 讲的是他们的商业模式（开源版 + 可选商业支持），不改变 MIT 的授权事实；
仓库里使用的 LVGL 9.5 就是 MIT 版本。只要保留版权与许可声明即可，没有 per-seat 费用。

- 写屏前显式 `powerOn()`，刷新后 `powerOff()`；SPI 总线与 SD/LoRa 共享时由面板类保持 CS。
- RGB565 先按 `LV_COLOR_16_SWAP` 还原字节序，再转亮度；4×4 Bayer 阈值 8..248 做 1bpp
  抖动，避免小字号文字整块丢失。

### 三色/四色面板

`board_display_colors()` 返回 1/3/4，UI 主题据此选择红色/黄色强调色；但**当前
`WalletBoardPort.cpp` 只有 1bpp 写屏路径**。如果定义了
`-DHEXWALLET_EPD_COLORS=3` 或 `4` 而没有对应的 GxEPD2 3C/4C 驱动类，初始化会明确失败，
不会把彩色面板按黑白类驱动。

要接入三色/四色面板，必须提供：

1. 面板型号、控制器（例如 UC8253/UC8151）、有效分辨率、颜色排列（黑/白/红或
   黑/白/红/黄）与 BUSY 极性；
2. 对应的 GxEPD2 驱动类（3C/4C 模板）或完整初始化/LUT 序列；
3. 实际排线：SCK/MOSI/CS/DC/RST/BUSY，以及是否与 SD/LoRa 共用 SPI；
4. 面板要求的全刷/局刷时序和最小刷新间隔。

没有这些证据时，代码只能保持黑白路径并 fail-closed。当前没有把任何三色/四色面板标记为
已验证。

## Arduino 工程布局

*Merged from docs/arduino-layout.md.*

用 Arduino IDE 打开根目录的 HexWallet.ino。草图文件夹应命名为 HexWallet。

`src/generated/` 保存编译时包含的数据文件。生产目录使用普通 `.inc` 名称，测试向量统一使用 `*Test.inc`。它们不是独立编译单元，由根目录 `.cpp` 显式包含；Arduino 打包时请保留整个 src 目录。

`tools/` 保存策略数据快照、1bpp 资源打包脚本、独立摘要向量生成器和原生网络清单生成器。
常规主机编译、目录导出与策略校验使用 PowerShell 和 C++；EVM 向量重生成另需 Node.js
及固定版本的 ethers，正常回归直接读取已提交向量。生成器与策略快照不烧进固件。

测试向量里的地址、掩码和秘密都是公开测试材料，禁止用于接收真实资产。`tests/` 保存主机
验证与交叉编译检查，不是链上交易验收的替代品；`build/`、对象文件和测试可执行文件属于
可重新生成的构建产物。

主控为 ESP32-P4NRW32X。PN7161 的 SPI/IRQ/VEN 引脚已按工程网络写进板级配置（见本文的
引脚表），不要用测试里的合成引脚去连硬件；合成引脚只用于让 NFC 代码在主机上被编译到。
功能完成度与未关闭的缺口见 [chain-support.md](chain-support.md) 与 [security-review-2026-10-28.md](record-security-review-2026-10-28.md)。

地址编码测试向量位于 `tests/fixtures/WalletForkAddressVectorsTest.inc`，使用公开私钥 1，禁止收款。仅 HEXWALLET_HOST_TEST 构建包含该文件，设备固件不包含它。
